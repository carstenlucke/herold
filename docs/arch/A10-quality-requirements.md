# 10 Quality Requirements

Chapter 10 collects the quality requirements that shape the architecture beyond the five headline quality goals of [§ 1.2](A01-introduction-and-goals.md#12-quality-goals). The authoritative, fit-criteria-bearing catalogue is the spec block [`N1 — Non-Functional Requirements`](../spec/N1-nichtfunktional.md) (Volere §§ 10–17); this chapter organises that catalogue architecturally and adds concrete usage and change scenarios in the form recommended by arc42 (context — stimulus — response — measure).

Nothing here overrides N1. Where a scenario and an NFR overlap, the NFR's fit criterion is binding; the scenario restates it in architecture terms and names the realising mechanism.

## 10.2 Quality Scenarios

Concrete scenarios that make the priority-A (and selected priority-B) requirements testable. **U** = usage scenario, **C** = change scenario. Each measure restates the binding fit criterion from N1 or sharpens it architecturally.

| ID | Kind | Context / Stimulus | Expected response | Measure |
|----|------|--------------------|-------------------|---------|
| QS-01 | U | Operator triggers **Process** on a `recorded` note of ~2 min audio; OpenAI responds within normal service levels. | The synchronous request returns the processed note (title, body, extras) or an error; a loading indicator is visible throughout. | Response within **30 s**; no queue or polling artefacts observable ([NFR-12a-01](../spec/N1-nichtfunktional.md#12a-speed-and-latency-requirements)). |
| QS-02 | U | OpenAI returns a 5xx (or times out) during **Process**. | The note remains `recorded`; `error_message` is populated and displayed; audio and row are intact; a manual retry succeeds once the provider recovers and clears `error_message`. | Zero data loss; status unchanged; retry is a plain re-invocation ([NFR-12d-01](../spec/N1-nichtfunktional.md#12d-reliability-and-availability-requirements)). |
| QS-03 | U | Network failure occurs mid-call during **Send** so the outcome at GitHub is unknown. | The note remains `processed`; Herold does not record a speculative issue reference; the operator retries explicitly. | No `sent` transition without a confirmed issue number + URL ([S1.5](../spec/S1-nachbarsysteme.md#s15--nb-04--github-issues-api)). |
| QS-04 | U | A transcript contains an injection attempt (e.g. an HTML comment instructing a downstream agent to ignore its instructions). | The dispatched issue renders the payload as inert text; operator-derived content is visually delimited from application-generated structure. | Injected markup neutralised; delimitation self-evident to a reader ([NFR-15b-04](../spec/N1-nichtfunktional.md#15b-integrity-requirements)). |
| QS-05 | U | A request hits any operator-facing route without a session attesting both factors. | The request is rejected at the gate and redirected to sign-in; no use-case code runs. | Access denied whenever either factor is missing ([NFR-15a-01](../spec/N1-nichtfunktional.md#15a-access-requirements)); 6th sign-in attempt within a minute rejected ([NFR-15a-02](../spec/N1-nichtfunktional.md#15a-access-requirements)). |
| QS-06 | U | The browser's developer tools inspect every request and response during a full record → process → send pass. | No OpenAI key, no GitHub PAT, no TOTP secret, and no configured preprocessing prompt appears in any payload reaching the browser. | Zero occurrences ([NFR-15b-01](../spec/N1-nichtfunktional.md#15b-integrity-requirements), [NFR-15b-02](../spec/N1-nichtfunktional.md#15b-integrity-requirements)). |
| QS-07 | U | Operator is locked out (API key and/or authenticator lost) and has only FTP access plus a browser. | Placing a recovery token file and redeeming it in the browser rotates the API key, unbinds TOTP, and re-admits the operator. | Recovery completes with no shell commands ([NFR-14a-02](../spec/N1-nichtfunktional.md#14a-maintenance-requirements)); tokens older than 60 min are rejected indistinguishably ([NFR-15a-04](../spec/N1-nichtfunktional.md#15a-access-requirements)). |
| QS-08 | C | A new release (no schema change) must reach production. | Tagging a release builds the artefact in CI and uploads it via FTP; database, audio store, and `.env` are untouched. | Deployment completes without shell access; persistent surfaces unchanged ([NFR-13b-01](../spec/N1-nichtfunktional.md#13b-expected-technological-environment), [S3.5](../spec/S3-inbetriebnahme.md#s35-ongoing-releases)). |
| QS-09 | C | The GitHub label and preprocessing prompt of an existing message type must change. | Editing the host configuration suffices; the next process/send run uses the new bindings. | Zero application-code edits ([NFR-14a-01](../spec/N1-nichtfunktional.md#14a-maintenance-requirements)). |
| QS-10 | C | The AI provider must be replaced (e.g. OpenAI → another vendor) for transcription and generation. | Only the two integration seams and host configuration change; controllers, models, UI, and pipeline orchestration stay untouched. | Change confined to one adapter per seam plus config ([NFR-14c-01](../spec/N1-nichtfunktional.md#14c-adaptability-requirements)). |
| QS-11 | C | A new `MessageTypeDT` value is added at spec level. | One new entry in the `config/herold.php` type catalogue (label, icon, GitHub label, extra-field schema, prompt); capture form, per-type validation, prompt resolution, and labelling follow automatically because every consumer resolves types through the configured catalogue. | One config entry, zero consumer edits ([QG-03](A01-introduction-and-goals.md#12-quality-goals), [N2.2](../spec/N2-querschnittskonzepte.md#n22-type-driven-configuration)); proven by the `TypeExtensionTest` acceptance tests. |
| QS-12 | U | The application log is inspected after a full pipeline pass including one failed provider call. | Operational entries reference notes by id only; the failure entry carries the reason but no transcript, content, or credential material. | No API key, token, transcript, or operator-derived content in any entry ([NFR-15b-03](../spec/N1-nichtfunktional.md#15b-integrity-requirements)). |

Scenario-to-goal traceability: QS-01–QS-03 substantiate [QG-02](A01-introduction-and-goals.md#12-quality-goals); QS-04–QS-07 and QS-12 substantiate [QG-05](A01-introduction-and-goals.md#12-quality-goals); QS-08 substantiates [QG-01](A01-introduction-and-goals.md#12-quality-goals); QS-09 and QS-11 substantiate [QG-03](A01-introduction-and-goals.md#12-quality-goals); QS-10 substantiates [QG-04](A01-introduction-and-goals.md#12-quality-goals).

# 11 Risks and Technical Debts

Identified technical risks and technical debts, ordered by priority within each group. Each entry names the trigger, the impact, and the mitigation stance. Accepted trade-offs that were *decided* (rather than accrued) are recorded as ADRs in [chapter 9](A09-architecture-decisions.md) and are not repeated as risks here unless a residual risk remains.

Project-level risks and assumptions (AS-01 …) live at spec level in [`P1 — Ziele & Rahmenbedingungen`](../spec/P1-ziele-rahmenbedingungen.md); this chapter covers the architecture-facing subset.

---

## 11.1 Risks

| ID | Risk | Trigger / Scenario | Impact | Mitigation stance |
|----|------|--------------------|--------|-------------------|
| R-01 | **Hard dependency on two external providers in one synchronous path.** Every *Process* crosses OpenAI twice, every *Send* crosses GitHub, all inside one HTTP request ([ADR-002](A09-architecture-decisions.md#adr-002-devprod-parity----apache--synchronous-processing)). | Provider outage, rate limiting, or latency spike. | The affected action fails or stalls until the PHP `max_execution_time` cuts it off; the operator is blocked for that action. | *Accepted.* Failure handling guarantees no data loss and safe manual retry ([N2.5](../spec/N2-querschnittskonzepte.md#n25-failure-handling)); single-user volume makes rate limits unlikely. No queue is added — that would contradict [QG-01](A01-introduction-and-goals.md#12-quality-goals). |
| R-02 | **Shared-hosting execution limits.** The host, not Herold, owns PHP limits (execution time, memory, upload size) and may change them. | A long recording pushes transcription past the host's execution ceiling; or host-side limit changes silently undercut the 30 s budget ([NFR-12a-01](../spec/N1-nichtfunktional.md#12a-speed-and-latency-requirements)). | *Process* aborts mid-pipeline; note stays `recorded` (no data loss), but the operator cannot complete long notes. | *Accepted with guardrail.* Herold targets task-intent notes, not lecture transcripts (NG-09); the 25 MB upload cap ([NFR-15a-03](../spec/N1-nichtfunktional.md#15a-access-requirements)) bounds the workload. Residual risk documented, not engineered away. |
| R-03 | **SQLite under a shared-hosting filesystem.** The database is one file on a host Herold does not control; hosting-side quirks around file locking or quotas are possible. | Concurrent requests (operator on two devices), disk-quota exhaustion, or a mid-write outage. | Write errors surface as failed requests; worst case is a corrupted database file. | *Accepted with operator duty.* Single-user write load is minimal; the deployment procedure treats pre-migration moments as snapshot points ([S3.6](../spec/S3-inbetriebnahme.md#s36-rollback-and-point-of-no-return)). Regular out-of-band backups of the persistent surfaces are an operator responsibility — no automated backup exists (see D-04). |
| R-04 | **FTP-based deployment has no transactionality.** A release replaces files one by one over FTP/TLS ([ORG-07](A02-architecture-constraints.md#22-organisational-constraints)); an interrupted upload leaves a mixed-version tree. | Network interruption mid-deploy; partial upload. | Application may be inconsistent until the upload is repeated; no automatic rollback. | *Accepted.* Re-running the workflow converges to the released state; schema-free releases are reversible by re-uploading the prior artefact ([S3.6](../spec/S3-inbetriebnahme.md#s36-rollback-and-point-of-no-return)). Single-user impact window is tolerable. |
| R-05 | **Prompt-injection reaches downstream agents despite sanitisation.** Sanitisation renders markup inert, but plain natural-language injection ("ignore previous instructions …") survives any markup-level filter by design. | A transcript or edit contains adversarial *text* (not markup) that a downstream agent follows. | An agent consuming the issue may act on injected instructions. | *Partially mitigated.* [NFR-15b-04](../spec/N1-nichtfunktional.md#15b-integrity-requirements) mandates visual delimitation of operator-derived content so consumers *can* distinguish content from instruction; residual risk lies with the agent's own guardrails — outside Herold's boundary ([ADR-003](A09-architecture-decisions.md#adr-003-github-issues-as-sole-ticket-store)). |
| R-06 | **Single-developer bus factor.** One person is operator, architect, and developer ([ORG-01](A02-architecture-constraints.md#22-organisational-constraints)). | Loss of availability or context. | Development stalls; operation continues (the deployed system needs no routine maintenance). | *Accepted.* Mitigated by exactly this documentation set: spec ([`docs/spec/`](../spec/)), architecture (this document), ADRs, and conventional commits keep the system reconstructible. |
| R-07 | **OpenAI model identifiers are hard-coded in the AI adapter.** `AIService` pins `gpt-4o-transcribe` (transcription) and `gpt-5.4-mini` (generation) in code, not in host configuration as [NFR-14c-01](../spec/N1-nichtfunktional.md#14c-adaptability-requirements) intends (see D-07). | OpenAI deprecates or renames either model. | *Process* fails with a provider error until a code change ships; no config-only remedy exists today. | *Contained by design.* All provider knowledge sits in the two seams of [`AIService`](A05-building-block-view.md) ([QG-04](A01-introduction-and-goals.md#12-quality-goals)), so the fix is a one-line change per seam. Repayment: lift the identifiers into `config/herold.php` (D-07). |

## 11.2 Technical Debts

| ID | Debt | Why it is debt | Repayment path |
|----|------|----------------|----------------|
| D-01 | **ADR backlog.** Several inherited decisions — application platform, database product, build toolchain, dev environment, AI-SDK choice — are recorded only as summarised constraints ([§ 2.1](A02-architecture-constraints.md#21-technical-constraints)) and backlog notes, not as first-class ADRs. | The rationale trail is thinner than for ADR-001…003; future revisiting requires archaeology. | Work off [`arch-backlog.md`](arch-backlog.md) item by item into [chapter 9](A09-architecture-decisions.md) / [`adr/`](../../adr/). |
| D-02 | **Framework-only schema remnants.** The `users` table carries `password`, `remember_token`, `email_verified_at` from Laravel scaffolding although Herold's auth model uses none of them ([relational data model](diagrams-png/relational-datamodel.png)). | Schema suggests auth flows that do not exist; a future reader may wire against them. | Drop the columns in a cleanup migration, or keep them documented as inert (current stance: documented in the datamodel diagram notes). |
| D-03 | **No automated end-to-end test against real providers.** Feature tests fake the OpenAI and GitHub boundaries; the true integration is exercised only by the manual smoke test ([S3.4](../spec/S3-inbetriebnahme.md#s34-first-commissioning) step 6, [S3.5](../spec/S3-inbetriebnahme.md#s35-ongoing-releases) step 4). | Provider-side contract drift (API or SDK behaviour) surfaces first in production. | Accepted for a personal tool; revisit if a provider change bites more than once. |
| D-04 | **No automated backup of the persistent surfaces.** Database, audio store, and `.env` survive releases but are not backed up by any mechanism Herold provides. | A host-side loss event is unrecoverable beyond what the hosting provider retains. | Operator-side scheduled FTP pull or host backup subscription; document the chosen procedure in the deployment view once established. |
| D-05 | **Spec/architecture status flags.** D1/D2 still carry a *draft* banner and F2's status legend predates completion; stale markers erode trust in an otherwise current documentation set. | Readers cannot tell current from stale at a glance. | Periodic documentation review; drop banners once blocks are confirmed stable. |
| D-06 | **Dead middleware `VerifyApiKey`.** `app/Http/Middleware/VerifyApiKey.php` exists but is registered nowhere; the protected routes rely on Laravel's stock session `auth` guard instead. | A reader may assume the class participates in the auth chain; unused security code invites false confidence. | Delete the class, or wire it deliberately and cover it with a test. |
| D-07 | **Spec/code drift.** Points where the implementation deviates from the binding spec (CONV-07 requires convergence): **(a)** failure is realised as a fourth status value `NoteStatus::ERROR` instead of the orthogonal `errorMessage`-only flag of [D2.5](../spec/D2-datentypen.md#d25-notestatusdt)/[N2.5](../spec/N2-querschnittskonzepte.md#n25-failure-handling) — retry semantics are equivalent (audio and transcript survive, tests prove re-processing), but the status machine differs; **(b)** markdown sanitisation runs only at the dispatch boundary (`send`), not additionally at the persistence boundaries of process/edit as [N2.7](../spec/N2-querschnittskonzepte.md#n27-content-sanitisation) schedules; **(c)** the upload rate limit is `throttle:10,60` (10/h) versus the 20/h of [NFR-15a-03](../spec/N1-nichtfunktional.md#15a-access-requirements); **(d)** the transcript is persisted in `voice_notes.transcript` although [UC-06](../spec/F2-anwendungsfaelle.md#uc-06--process-voice-note) postconditions state it is not retained; **(e)** [TECH-08](A02-architecture-constraints.md#21-technical-constraints) and `CLAUDE.md` name `laravel/ai` as the AI SDK, but the code integrates OpenAI via the plain `Http` facade; **(f)** model identifiers are hard-coded (R-07) versus host-configured per [NFR-14c-01](../spec/N1-nichtfunktional.md#14c-adaptability-requirements); **(g)** successful recovery renders the new API key but establishes no session — the operator signs in afresh — whereas [UC-03](../spec/F2-anwendungsfaelle.md#uc-03--recover-access) postulates an authenticated session as postcondition. | Divergent documents mislead future changes on exactly the load-bearing concepts (failure handling, sanitisation, portability). | Per item: either amend the spec to match the implemented behaviour or adjust the code — each is a small, isolated change; decide direction case by case and keep [chapter 8](A08-cross-cutting-concepts.md) as the code-accurate reference meanwhile. |

## 11.3 Non-risks

Recorded to pre-empt recurring questions; each is a deliberate scope decision, not an unmanaged exposure.

- **Scalability.** Single operator by constraint ([ORG-02](A02-architecture-constraints.md#22-organisational-constraints), [CON-3a-04](../spec/P1-constraints.md#con-3a-04-single-user-system)); load beyond one user is out of scope, hence not a risk.
- **Loss of a dispatched ticket.** After `sent`, GitHub owns the issue; its durability is GitHub's concern ([ADR-003](A09-architecture-decisions.md#adr-003-github-issues-as-sole-ticket-store)).
- **Blocking requests during processing.** A consequence of [ADR-002](A09-architecture-decisions.md#adr-002-devprod-parity----apache--synchronous-processing), bounded by [NFR-12a-01](../spec/N1-nichtfunktional.md#12a-speed-and-latency-requirements) and accepted as the price of QG-01; the risk that remains (provider stall, host limits) is covered by R-01/R-02.
